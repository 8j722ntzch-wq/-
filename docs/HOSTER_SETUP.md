# hoster.by: подключение baltmotors.by

## Текущее состояние
- Репозиторий: https://github.com/8j722ntzch-wq/-
- Домен: baltmotors.by.
- Основная ветка: master. Разработка: development.
- План выпуска: development → Pull Request → master → сборка → SFTP.
- На момент настройки в ветках нет исходников сайта, package.json или lock-файла.
- Astro, его версия и команды сборки для этого репозитория пока не подтверждены.
- Автоматическая публикация не включена. SFTP ещё не проверен.
- main сохранена; удаление веток не требуется.

Методология Revolis.Мото используется как образец. Сервер vh132.hoster.by,
логин github-deploy и пути revolis.by относятся к прежнему проекту.
Не переносить их без подтверждения применимости к baltmotors.by.

## 1. Реквизиты
Добавить Repository secrets:
https://github.com/8j722ntzch-wq/-/settings/secrets/actions

| Secret | Значение |
|---|---|
| SFTP_HOST | Подтверждённый сервер hoster.by для baltmotors.by, без схемы и пути |
| SFTP_PORT | Порт SFTP; при отсутствии секрета используется 22 |
| SFTP_USERNAME | Полный логин аккаунта с SFTP-доступом |
| SFTP_PASSWORD | Пароль этого аккаунта; вводить только в GitHub Secrets |
| SFTP_KNOWN_HOSTS | Проверенная строка/строки OpenSSH known_hosts для сервера |

SFTP_KNOWN_HOSTS — не один отпечаток SHA256, а запись вида
`hostname ssh-ed25519 BASE64_PUBLIC_KEY`.
Для нестандартного порта имя должно иметь вид `[hostname]:port`.
Ключ и его SHA256-отпечаток сверить с поддержкой hoster.by.
Сам по себе результат ssh-keyscan не подтверждает подлинность ключа.

Созданный в панели FTP-пользователь не обязательно поддерживает SFTP.
Нужно подтвердить тип аккаунта, полный логин и возможность входа по паролю.
Не сохранять пароли, приватные ключи, .env и резервные копии сайта в Git.

## 2. Проверка без изменений на хостинге
Actions → SFTP connection check (read only) → Run workflow → master.

Workflow запускается только вручную на master; выполняет только:
`pwd`, `ls -la`, `bye`.
Проверка ключа сервера обязательна; файловые операции записи отсутствуют.
Вывод каталогов попадёт в журнал Actions публичного репозитория.
У аккаунта должен быть доступ только к предназначенному каталогу сайта.

Успешная проверка подтверждает авторизацию и чтение начального каталога,
но не права записи и не принадлежность каталога домену.
По выводу и настройкам сайта в панели определить каталог именно baltmotors.by.
Если это стартовый каталог SFTP, будущий SFTP_REMOTE_DIR будет `./`.
Не подставлять автоматически `/www/baltmotors.by` или пути revolis.by.

## 3. Включение публикации после проверки
1. Подтвердить успешный SFTP-вход и каталог baltmotors.by.
2. Добавить исходники сайта и lock-файл в development.
3. Подтвердить фреймворк, версию Node и команды check/build.
4. Для статического Astro проверить output: static и выходной dist/index.html.
5. Настроить CI для PR в master: npm ci → npm run check → npm run build
   (команды применимы только при наличии соответствующего package.json).
6. Сохранить проверенную резервную копию текущего сайта и, если есть CMS, базы.
7. Добавить SFTP_REMOTE_DIR с проверенным путём.
8. Создать .github/workflows/deploy.yml: push в master и ручной запуск;
   загрузка только содержимого dist; обязательная проверка host key.
9. Первый релиз проводить после подтверждения назначения каталога.
   Не включать рекурсивное удаление файлов по умолчанию.
10. Проверить HTTPS, главную, вложенные страницы, изображения и формы.

Для защиты master рекомендуется требовать PR и успешную проверку сборки,
когда такая проверка появится. Не требовать несуществующий статус CI.
Не требовать одобрение второго человека, если репозиторий ведёт один владелец.

## Диагностика
- Authentication failed: логин, пароль, тип пользователя и разрешение SFTP.
- Host key verification failed: сверить ключ с hoster.by; не отключать проверку.
- Connection refused / timeout: сервер, порт, служба SSH и сетевые ограничения.
- Missing repository secret: добавить секрет с точным именем из таблицы.
- Успешная проверка не означает, что сайт опубликован.

FTP/FTPS actions не заменяют SFTP-клиент. Node на статическом хостинге не нужен:
сборка будет выполняться в GitHub Actions. Обработка заявок требует отдельного решения.
